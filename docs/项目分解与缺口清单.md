## 一、项目终态蓝图（8 周后要交付什么）

一句话：**一个能上线、有公开链接、带量化对比数据的知识库问答产品。**

```
┌─────────────────────────────────────────────────────────────┐
│  用户浏览器                                                    │
│    ↓ 输入问题                                                 │
│  Web 界面（HTML/JS）                                          │
│    ↓ HTTP POST /ask                                          │
│  FastAPI 服务                                                 │
│    ├─ 检索层：向量检索 + 关键词检索 → 融合排序                    │
│    ├─ 重排层：Rerank 精排 Top-50 → Top-5                        │
│    ├─ 生成层：DeepSeek 组织答案 + 引用编号                       │
│    └─ 返回：{answer, sources[]}                               │
│    ↑                                                          │
│  向量库（ChromaDB / numpy 手写余弦相似度）                       │
└─────────────────────────────────────────────────────────────┘
         ↑
  部署到云 → 拿到公开链接 → 放进简历
```

## 三、缺口汇总（按优先级排序）

### 🔴 P0 —— 不做就会出事

1. **git 仓库未初始化**。项目从 9/26 做到现在，**一次版本提交都没有**。这是最大的风险：硬盘一坏、改错一次，全部归零。而且求职时 HR/面试官要看 GitHub 提交记录，没有 commit 历史等于这段经历"不可验证"。
2. **语料规模太小**。当前只有 5 个块，IDF 计算公式 `log((5+1)/(df+1))+1` 严重失真——一个词只要出现在 3 个块里，IDF 就掉到 1.69。**现在 README 里那组"折半查找 27.65 / 哈希表存满 7.74"的对比数据，放到真实文档上会完全变样**，面试官一问"你当时多少块"就露底。必须先换一本真教材/手册重跑，再谈调参。
3. **没有任何测试**。改分词器或改切块逻辑，只能靠肉眼看输出，错了不知道。

### 🟡 P1 —— 决定项目能走多远

4. **阶段 3 全部没做**（FastAPI + 网页 + 上线）。这是"两个可上线全栈产品"目标里**唯一能变成链接的那一半**，也是简历上唯一能让面试官亲手点的东西。
5. **没有评估集**。阶段 2 和阶段 4 都要靠"变好了多少"来说话，没有标注集就只能吹主观感受。
6. **`docs/` 目录是空的**。项目笔记、设计决策、踩坑记录全在代码注释里，没有对外可读的文档。

### 🟢 P2 —— 加分项，可延后

7. Rerank 精排、混合检索（RRF）、多轮对话、PDF 上传接口。

### ⚠️ 一处需要修正的矛盾

`README.md` 第 36 行写的是：

> 不用向量数据库：安装易踩坑、收益不明显。第 4 阶段用 numpy 手写余弦相似度

而 `.env` 里已经出现了 `EMBEDDING_BACKEND` / `EMBEDDING_DIM`，且配置项注释明确提到 ChromaDB 风格的方案。**两处口径不一致**，建议统一：要么 README 补上"Embedding 后端"这一节，要么明确写"第 4 阶段只做 numpy 手写，不引入向量库"。

另外 `requirements.txt` 把 numpy 注释掉并写着"到那一周再装"，但 `.env` 已经把 `EMBEDDING_BACKEND=local` 当成"可立即跑通全链路"的默认值——**实际上现在没有任何代码读这个变量**，属于"配置先行、实现未到"。
